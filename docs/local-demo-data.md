# Local demo data

ชุดนี้มีไว้ให้ลอง ERP (และจอสถานีเมื่อออกแบบใหม่เสร็จ) บนเครื่องโดยไม่แตะฐาน Supabase ที่ใช้ร่วมกัน

## ขอบเขตความปลอดภัย

- ยอมทำงานเฉพาะ PostgreSQL `127.0.0.1:5433/anajak_erp_demo`
- `npm run db:seed:demo` ล้างเฉพาะข้อมูลธุรกิจในฐาน demo แล้วสร้างใหม่ทั้งชุด
- เก็บ User mapping สำหรับ Supabase login รวมถึง Pattern, PackagingOption และ ServiceCatalog
- ล้าง Product/ProductVariant เดิมในฐาน demo แล้วสร้างเฉพาะสินค้า `DEMO-*` พร้อมยอดทดสอบใหม่ทุกครั้ง จึงไม่ใช้ mirror จาก Anajak Stock
- ฐาน demo ต้องไม่มี `stock_api_url` หรือ `stock_api_key`; ถ้ามี script จะหยุดก่อนล้างข้อมูล
- local stock writer เปิดได้เมื่อทั้ง `ANAJAK_ERP_DEMO_MODE=1` และ DATABASE_URL ตรงฐาน demo เท่านั้น; flag ที่ชี้ฐานอื่นจะหยุดก่อนอ่านหรือเขียนข้อมูล
- หน้า Products/Settings ซ่อนการ Sync และช่อง API ในโหมด demo; outbound Stock request ถูกปิดอีกชั้นก่อน `fetch`
- ชื่อลูกค้า บริษัท เบอร์โทร อีเมล และเอกสารทั้งหมดเป็นข้อมูลสมมติ
- canonical `npm run db:seed` ยังเป็น master data เท่านั้น และไม่ล้างข้อมูลธุรกิจ

## ใบผลิตในฐานทดลองเป็น "แบบเดิม" (ตั้งแต่ 2026-09-09)

- เว็บจริงยังเปิดใบผลิตแบบเดิม (`PRODUCTION_V2_ENABLED=0`) ฐานทดลองจึงต้องเหมือนกัน: seed สร้าง scenario ครบแล้ว **ถอด flag V2 ออกจากทุกขั้นและลบเลข MO** ฟอร์มใบผลิต `/production/[id]` (เริ่ม/ปิดขั้น/กรอกยอด/ย้อน) จึงกดได้ทุกใบ
- ออเดอร์ที่ยังอยู่คิว (`ORD-<งวด>-0003`) ไม่มีใบผลิตในโหมดแบบเดิม = ลอง “เปิดใบผลิต” จากหน้าการผลิตได้ (V2 เท่านั้นที่ปล่อยใบไว้ล่วงหน้า)
- จะซ้อม Production V2 (ใบ MO · ledger · จอสถานีใหม่ตาม ROADMAP §B) ให้ seed ด้วย `DEMO_PRODUCTION_V2=1 npm run db:seed:demo` — ใบทุกใบกลับเป็น V2 และฟอร์มใบผลิตจะปฏิเสธปุ่มสถานะ (กติกาเดิม)

## คำสั่งที่ใช้ประจำ

```bash
npm run db:seed:demo
npm run dev:demo
```

ทั้งสองคำสั่งอ่าน user/password จาก Docker container `anajak-postgres` โดยไม่พิมพ์ค่าออกมา และบังคับฐานเป้าหมายผ่าน `src/lib/demo-seed-plan.ts`

## สิ่งที่ต้องมีครั้งแรก

ฐาน `anajak_erp_demo` ต้องถูกสร้างและ apply migrations ครบก่อน จากนั้นต้องมี active OWNER ที่ `supabaseId` ตรงกับ session ของผู้ทดสอบ Script จะ fail closed หากเงื่อนไขนี้ไม่ครบ และจะไม่พยายามสร้างบัญชี Supabase หรือนำ Product/credential จาก Stock เข้ามาเอง

## ภาพวันทำงานที่สร้าง

- 27 ออเดอร์ (15 สถานการณ์ + 12 ใบให้กดไล่จากต้น) ตั้งแต่ inquiry, ออกแบบ, รอเปิดผลิต, กำลังผลิต, QC, แพ็ก, พร้อมส่ง, ส่งแล้ว และเสร็จสิ้น
- 24 ใบผลิต / 81 ขั้น พร้อมงานรับเสื้อ, เบิกสต๊อกทดสอบ, DTF, รีดร้อน, blocked stock และร้านนอกเกินกำหนด
- Print Run กำลังพิมพ์ 1, รอตัดแยก 1 และประวัติเสร็จแล้ว 2 รอบ โดย DTF ที่ปิดแล้วทุกขั้นมี item หลักฐาน
- QC, Delivery, Invoice, Payment, Billing Note, Notification และ Audit ที่สัมพันธ์กับออเดอร์จริง
- สินค้าทดสอบพร้อมเบิก `DEMO-POLO-READY` มี 24 ตัวต่อไซส์ S/M/L; สินค้าขาดจริง `DEMO-TEE-SHORT` มี L เพียง 6 ตัว

## ใบผลิตตัวอย่าง "กดไล่จากขั้นแรก" (ORD-<งวด>-0016 … 0027 · `prisma/seed-demo-form-states.ts`)

ทุกใบเริ่มที่สถานะแรก (ออเดอร์กำลังผลิต · ทุกขั้นยังไม่เริ่ม) ต่างกันที่เส้นทาง — ชื่อลูกค้า = ชื่อเส้นทาง เห็นจากหน้ารายการผลิตและหัวใบ · เปิดตรง `/production/demo-production-form-<key>`

| # | key | เส้นทาง |
|---|---|---|
| 1 | `press` | รีดร้อน → ตรวจ (สั้นสุด: เริ่ม → ติ๊ก → ยอด → ปิด → ส่งเข้า QC) |
| 2 | `receive` | เสื้อลูกค้า (ใบตรวจรับ) → รีดร้อน → ตรวจ |
| 3 | `tag-press` | ป้ายคอร้านนอก → รีดร้อน → ตรวจ (ร้านนอกไปก่อน รีดได้เมื่อของกลับ) |
| 4 | `embroidery` | ปักร้านนอก → ตรวจ (ส่งร้าน → รับงานกลับ) |
| 5 | `screen-tag` | สกรีนร้านนอก → ป้ายคอร้านนอก → ตรวจ |
| 6 | `pair` | ช่องคู่: พับป้าย + ปักแขน → ตรวจ |
| 7 | `long` | เสื้อลูกค้า → ปัก → รีดร้อน → ตรวจ → แพ็ก |
| 8 | `sewing` | ตัดเย็บร้านนอก → ตรวจ |
| 9 | `sublimation` | ซับลิเมชันร้านนอก → ตรวจ |
| 10 | `single` | ขั้นเดียว: ติดสติกเกอร์ → ส่งเข้า QC |
| 11 | `dtf` | รับเสื้อลูกค้า + พิมพ์ DTF เดินคู่กัน → รีด → QC |
| 12 | `dtf-batch` | พิมพ์ DTF รวมรอบกับใบ 11 → รีด → QC |

DTF และร้านนอกลงมือผ่านกล่องในใบผลิตได้เลย ส่วน QC และแพ็กใช้พื้นที่จริงในออเดอร์ ไม่เพิ่มขั้น CUSTOM ตรวจ/แพ็กซ้ำ ใบที่เสื้อพร้อมมีใบรับจำนวนครบเป็นหลักฐาน; ใบตัดเย็บใช้แหล่งเสื้อสั่งผลิต เลขออเดอร์รันต่อจากใบสุดท้ายในชุดทดลอง

## ลอง flow สต๊อก

1. เปิดใบผลิต `/production/demo-production-stock-pick-ready` (`ORD-<งวด>-0015`)
2. กด **เบิกเสื้อที่ยังขาด 24 ตัว** ค่าเริ่มต้นเผื่อเสียเป็น 9/9/9; ledger จะออกเลข `DEMO-ISSUE-*` และขั้นปิดที่ 24/24
3. เปิดแท็บสินค้าในใบผลิต แล้วกด **คืนเศษ** เพื่อคืนส่วนเกิน; ledger จะออกเลข `DEMO-RETURN-*`
4. เปิดออเดอร์ `ORD-<งวด>-0008` จาก `/orders` แล้วกดเข้าใบผลิต เพื่อดูงานติดปัญหาจากสต๊อก L ที่ขาดจริง

การเบิก/คืนเปลี่ยน `ProductVariant.stock`, `ProductVariant.totalStock`, `Product.totalStock`, MaterialUsage และ audit ใน transaction เดียว พร้อมกันยอดจองของออเดอร์อื่นไว้ หากต้องการเริ่มใหม่ให้รัน `npm run db:seed:demo` อีกครั้ง

## กรณีที่ใช้ตรวจ A16

- รับเสื้อ 45 + 15 จนครบ 60; รับตำหนิ คืนเฉพาะตำหนิ รับทดแทน และแก้ยอดพร้อมกดซ้ำ
- รวม DTF สองใบ 120 ตัว; ฟิล์มเสีย 3 → พิมพ์เพิ่ม 3 → รีดได้เมื่อฟิล์มดีครบ
- รีดดี 58 เสีย 2 → QC ระบุ L 2 → งานแก้แสดงเฉพาะ L 2 → ตรวจซ้ำ → แพ็ก
- ร้านนอกส่ง 10 รับดี 8 เสีย 2 → ยืนยันเฉพาะ 8 → เปิดส่งแก้ 2
- เครื่องเสียระหว่าง DTF ทำดีแล้ว 4/10 → ยกเลิกรอบค้าง → ส่งร้านแทนเฉพาะ 6 → กลับมาทำขั้นต่อไป
- แพ็กแบ่งใบส่ง 50/10 ตัว ตรวจไม่ให้จำนวนซ้ำหรือเกินออเดอร์
- ส่งครบแล้วรับคืน L 2 จากใบส่ง 10 ตัว → ตรวจเฉพาะ L 2 → เปิดใบส่งทดแทน 2 ตัว โดยอีก 58 ตัวยังอยู่กับลูกค้า

สคริปต์ `verify-qc.ts`, `verify-pack.ts`, `verify-print-run.ts`, `verify-qc-returns.ts` สร้างข้อมูลทดสอบ ต้องกำหนด DATABASE_URL ไปฐาน local demo ข้างต้นโดยตรงก่อนรัน ห้ามใช้ค่า remote จาก `.env` กับการตรวจรอบนี้
