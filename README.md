# Anajak ERP

ระบบหลังบ้านโรงงานสกรีนเสื้อ Anajak สำหรับขาย ออกแบบและอนุมัติแบบ ผลิตและส่งร้านนอก ตรวจคุณภาพ แพ็กและส่ง ไปจนถึงบิล ภาษี และลูกหนี้ ใช้ร่วมกับการทำงานและเอกสารจริงของโรงงาน

เจ้าของ หัวหน้า และทีมขายใช้โต๊ะงานบนคอมพิวเตอร์; ทีมผลิตใช้มือถือหรือจอทัช ลูกค้าและร้านนอกเปิดลิงก์เฉพาะงานโดยไม่ต้องมีบัญชี ERP งาน DTF ทำเองได้ ส่วนเทคนิคอื่นส่งร้านนอก และสามารถส่งขั้นที่ปกติทำเองออกไปได้เมื่อจำเป็น

## ขอบเขตและเอกสาร

ระบบเชื่อม Supabase สำหรับบัญชีผู้ใช้และไฟล์, PostgreSQL สำหรับข้อมูลธุรกิจ, Anajak Stock สำหรับสินค้าและสต๊อก และ Vercel สำหรับเว็บและงานตามเวลา รองรับงาน B2B เครดิตเทอมและเอกสารภาษีไทย ส่วนออเดอร์จากเว็บสกรีนเสื้อในอนาคตต้องเข้ากระบวนการเดียวกับออเดอร์หน้าร้าน

ขอบเขตนี้ไม่รวมบัญชีแยกประเภท ต้นทุนต่อออเดอร์ ระบบแชต โปรแกรมออกแบบเสื้อ หรือระบบคลังสินค้าที่ซ้ำกับ Anajak Stock กฎและข้อยกเว้นฉบับเต็มอยู่ใน SPEC

| อ่านเรื่อง | ไฟล์หลัก |
|---|---|
| พฤติกรรมระบบ เกณฑ์รับงาน สิทธิ์ และข้อยกเว้น | [SPEC.md](SPEC.md) |
| งานที่กำลังทำ ผลตรวจ สิ่งที่ติด และคิว | [ROADMAP.md](ROADMAP.md) |
| ข้อตกลงการแก้โค้ดและตำแหน่งโค้ดสำคัญ | [AGENTS.md](AGENTS.md) |
| ทิศทางหน้าจอและชุดสี/ตัวอักษรที่ใช้อยู่ | [DESIGN.md](DESIGN.md) |
| คำสั่งและรุ่นแพ็กเกจที่ติดตั้ง | [package.json](package.json) และ [package-lock.json](package-lock.json) |

## เตรียมเครื่องและเปิดเว็บ

ใช้ Node.js 24 และ npm ให้ตรงกับ [CI](.github/workflows/ci.yml) โค้ดใช้ Next.js, React, tRPC, Prisma, Tailwind CSS และชุดคอมโพเนนต์จาก Radix/shadcn

1. ติดตั้งแพ็กเกจด้วย `npm ci` ซึ่งสร้าง Prisma client ผ่าน `postinstall` ให้ด้วย
2. ถ้ายังไม่มี `.env` ให้คัดลอก `.env.example` เป็น `.env` แล้วตั้งค่าของสภาพแวดล้อมที่จะใช้; หากมีอยู่แล้วให้ตรวจชื่อรายการที่ขาดโดยไม่คัดลอกทับไฟล์เดิม
3. เตรียม PostgreSQL ที่มี migrations ครบและบัญชี Supabase ที่ผูกกับแถว User ของ ERP แล้ว ก่อนเปิดเว็บ ให้เลือกชัดเจนว่าจะใช้ฐานพัฒนาเฉพาะงานหรือฐาน demo ตามหัวข้อถัดไป
4. รัน `npm run dev` แล้วเปิด URL ที่ Next.js แสดง ปกติคือ [localhost:3000](http://localhost:3000) คำสั่งนี้ใช้ฐานตาม `DATABASE_URL` ในสภาพแวดล้อม จึงอาจเป็นฐานที่ใช้งานร่วมกันได้

| ตัวแปร | ใช้ทำอะไร |
|---|---|
| `DATABASE_URL` | การเชื่อม PostgreSQL ของแอป |
| `DIRECT_URL` | การเชื่อมตรงสำหรับ Prisma migrations ตาม [schema](prisma/schema.prisma) |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase Auth ฝั่งเบราว์เซอร์ |
| `SUPABASE_SERVICE_ROLE_KEY` | งานฝั่งเซิร์ฟเวอร์ เช่น จัดการผู้ใช้และออก URL อ่านไฟล์ |
| `NEXT_PUBLIC_APP_URL` | URL ของแอปในสภาพแวดล้อมนั้น |
| `CRON_SECRET` | ตรวจสิทธิ์เรียกงานบิลเกินกำหนดและปลดจองสต๊อกค้าง; ไม่ตั้งจะได้ 401 ทั้งสอง route |
| `PRODUCTION_V2_ENABLED` | สวิตช์เปิด Production V2; ตัวอย่างเริ่มที่ `0` การเปิดใช้จริงต้องผ่านแผนเปลี่ยนระบบใน ROADMAP |
| `ANAJAK_STOCK_API_URL`, `ANAJAK_STOCK_API_KEY` | ค่าทางเลือกสำหรับ Stock; ระบบอ่าน Settings → Stock ก่อน แล้วจึงใช้ env เป็นค่ารอง |

เก็บค่าลับไว้ในไฟล์ env ที่ไม่เข้า Git หรือค่าตั้งของผู้ให้บริการ ห้ามใส่ service role key หรือข้อมูลเชื่อมฐานในตัวแปรที่ขึ้นต้น `NEXT_PUBLIC_`

สำหรับฐานพัฒนาใหม่ ให้ใช้ migrations ที่มีใน [prisma/migrations](prisma/migrations) เมื่อเปลี่ยน schema ใช้ `npm run db:migrate` บนฐานพัฒนาเฉพาะงาน; คำสั่งนี้คือ `prisma migrate dev` และไม่ใช่คำสั่งติดตั้งฐาน Production ส่วน `npm run db:seed` เติมข้อมูลแม่ เช่น จุดทำงานและบริการ โดยไม่ล้างออเดอร์หรือสร้างข้อมูลธุรกิจตัวอย่าง อ่าน [prisma/seed.ts](prisma/seed.ts) ก่อนรันกับฐานที่มีข้อมูล

ระบบไม่มีสมัครสมาชิกสาธารณะ ผู้ใช้รายถัดไปสร้างจาก Settings → ผู้ใช้ สำหรับระบบใหม่มี [scripts/create-owner.ts](scripts/create-owner.ts) เพื่อสร้างและผูก OWNER คนแรก ต้องใช้บัญชีที่ตั้งใจให้เป็นเจ้าของจริง: รันกับอีเมลที่มีอยู่แล้วจะเปลี่ยนรหัสผ่านใน Supabase และยกสิทธิ์ ERP เป็น OWNER ด้วย หลังเตรียมแล้วตรวจล็อกอินและการผูก `supabaseId` จริง

## ฐานทดลองบนเครื่อง

โหมด demo แยกข้อมูลธุรกิจและสต๊อกไปที่ PostgreSQL `127.0.0.1:5433/anajak_erp_demo` ส่วนการล็อกอินและไฟล์ยังอาศัยค่าของ Supabase ที่ตั้งไว้ ไม่ใช่ระบบออฟไลน์หรือ Supabase จำลองทั้งชุด

ก่อนใช้ครั้งแรกต้องมี Docker container ชื่อ `anajak-postgres` ที่เปิด PostgreSQL บนพอร์ตดังกล่าว, สร้างฐาน `anajak_erp_demo` และติดตั้ง migrations ครบ พร้อม active OWNER ที่มี `supabaseId` ตรงกับผู้ทดสอบ สคริปต์ demo ไม่สร้างฐานหรือบัญชี Supabase ให้เอง และต้องไม่มีรายการ `stock_api_url` หรือ `stock_api_key` ในตาราง Settings ของฐานนี้ แม้ค่าเป็นว่างก็จะถูกปฏิเสธ

เมื่อเตรียมครบและต้องการเริ่มข้อมูลธุรกิจทดลองใหม่:

```bash
npm run db:seed:demo
npm run dev:demo
```

`db:seed:demo` ล้างข้อมูลธุรกิจในฐาน demo รวมถึง Product/ProductVariant แล้วสร้างสินค้า `DEMO-*` และสถานการณ์ใหม่ทุกครั้ง เก็บตาราง User, Settings, Agent API keys, Pattern, PackagingOption, ServiceCatalog และประวัติ migrations ตาม [รายการที่สคริปต์รักษาไว้](src/lib/demo-seed-plan.ts) จึงต้องถือว่าการแก้ข้อมูลทดลองก่อนหน้าจะหายไป

[ตัวเรียก demo](scripts/run-local-demo.ts) อ่านชื่อผู้ใช้และรหัสผ่านจาก container โดยไม่พิมพ์ค่าออกมา บังคับทั้ง `DATABASE_URL` และ `DIRECT_URL` ให้ตรงฐาน demo และเปิด `ANAJAK_ERP_DEMO_MODE=1` การเบิก/คืนสต๊อกในโหมดนี้ตรวจฐานปลายทางก่อนทำงาน และตัวเชื่อม Stock ปิดคำขอออกไปภายนอกอีกชั้น หน้า Products/Settings ซ่อนการ Sync และช่องเชื่อม Stock

หยุด dev server ตัวเดิมก่อนเปลี่ยนระหว่าง `dev` กับ `dev:demo` ทั้งคู่ใช้พื้นที่ build เดียวกัน อย่าสรุปว่าใช้ฐานทดลองจากชื่อแท็บหรือพอร์ตอย่างเดียว

### ชุดงานที่มีให้ลอง

[scenario หลัก](src/lib/demo-seed-plan.ts) ครอบคลุมสอบถาม ออกแบบ รอเปิดผลิต รับเสื้อ พิมพ์ DTF รีดร้อน สต๊อกขาด ร้านนอกเกินกำหนด QC แพ็ก ส่ง และปิดงาน พร้อมข้อมูลรอบพิมพ์ บิล การรับเงิน ใบวางบิล การแจ้งเตือน และหลักฐานที่สัมพันธ์กัน ข้อมูลลูกค้าและเอกสารตัวอย่างเป็นข้อมูลสมมติ จำนวนหลัง seed ให้ดูผลที่สคริปต์แสดง แทนการใช้ตัวเลขจากรายงานเก่า

ค่าเริ่มต้นของ seed เป็นใบผลิตแบบเดิม: ปิด `executionEnabled` และเอาเลข MO ออก ออเดอร์คิว `demo-order-production-ready` ยังไม่มีใบผลิต จึงใช้ลองเปิดใบผลิตจาก `/production` ได้ หัวหน้าใช้ `/production/[id]` ส่วนบัญชีช่างผลิตที่ไม่มีสิทธิ์หัวหน้าจะถูกพาไปหน้าลงมือที่ `/production/floor` และ `/station` เดิมส่งต่อมาหน้านี้

[ชุดใบผลิตสำหรับเริ่มจากขั้นแรก](prisma/seed-demo-form-states.ts) เพิ่มเส้นทางต่อไปนี้ ทุกใบเป็นแบบเดิมและเริ่มทุกขั้นที่ยังไม่ทำ เปิดด้วย `/production/demo-production-form-<key>`; ชื่อลูกค้าในรายการบอกเส้นทางเดียวกัน

| key | เส้นทางทดลอง |
|---|---|
| `press` | รีดร้อน → ตรวจ |
| `receive` | ตรวจรับเสื้อลูกค้า → รีดร้อน → ตรวจ |
| `tag-press` | ป้ายคอร้านนอก → รีดร้อน → ตรวจ |
| `embroidery` | ปักร้านนอก → ตรวจ |
| `screen-tag` | สกรีนร้านนอก → ป้ายคอร้านนอก → ตรวจ |
| `pair` | ช่องคู่ พับป้าย + ปักแขน → ตรวจ |
| `long` | เสื้อลูกค้า → ปัก → รีดร้อน → ตรวจ → แพ็ก |
| `sewing` | ตัดเย็บร้านนอก → ตรวจ |
| `sublimation` | ซับลิเมชันร้านนอก → ตรวจ |
| `single` | ติดสติกเกอร์ขั้นเดียว → ส่งเข้า QC |

ชุดเริ่มจากขั้นแรกไม่มีเส้นทางพิมพ์ DTF ส่วนสถานการณ์ `dtf-printing`/`dtf-printed` ในชุดหลักมีข้อมูลรอบพิมพ์ให้ตรวจ ต้องทดสอบหน้าสถานีและรอบพิมพ์ตามเกณฑ์ใน ROADMAP ก่อนสรุปว่าลองเส้นทาง DTF ครบแล้ว

ตัวเลือก `DEMO_PRODUCTION_V2=1 npm run db:seed:demo` มีไว้ซ้อม V2 แต่จาก source ชุด form ยังสร้างใบแบบเดิม ขณะที่ตัวตรวจ V2 กำหนดให้ทุกใบมีเลข MO จึงมีเงื่อนไขขัดกันที่ต้องตรวจและแก้ก่อนพึ่งตัวเลือกนี้ รายการตรวจอยู่ ROADMAP; การอ่านโค้ดนี้ยังไม่ใช่ผลรัน seed V2

### ลองเบิกและคืนสต๊อก

1. เปิด `/production/demo-production-stock-pick-ready` ซึ่งใช้ `DEMO-POLO-READY` งานต้องการ S/M/L รวม 24 ตัว และเริ่มด้วยสต๊อก 24 ตัวต่อไซส์
2. ใช้การ์ดเบิกเสื้อ ตรวจยอดเผื่อเสียก่อนยืนยัน ค่าเริ่มต้นของงานนี้คือ 9/9/9 และบันทึกเบิกจะได้เลข `DEMO-ISSUE-*` ตรวจว่าระบบนับงานครบ 24 ตัว
3. ใช้ **คืนเศษ** ในการ์ดเดิมเพื่อคืนส่วนเกิน ตรวจยอดคงเหลือและบันทึก `DEMO-RETURN-*` แทนการอ้าง URL แท็บเก่าที่อาจไม่ได้เลือกการ์ดให้แล้ว
4. เปิด `/orders/demo-order-blocked-stock` แล้วเข้าใบผลิต ดู `DEMO-TEE-SHORT` ที่ไซส์ L มีเพียง 6 ตัว ตรวจข้อความว่าส่วนใดขาดและการป้องกันเบิกเกินของที่ใช้ได้

การเบิก/คืนปรับยอด ProductVariant, ยอดรวม Product, MaterialUsage และ audit ใน transaction เดียว พร้อมหักยอดจองของออเดอร์อื่นก่อนคำนวณของที่ใช้ได้ ต้องตรวจทั้งหน้าจอและรายการเคลื่อนไหวเพื่อยืนยันผล รัน seed demo ใหม่เมื่อตั้งใจล้างรอบทดลองนี้

## คำสั่งตรวจและ build

```bash
npm run lint
npm run typecheck
npm test
npm run verify:ui
```

`npm test` รัน Vitest ใน [src](src) ส่วน `verify:ui` ตรวจชุดสี/คอมโพเนนต์ ลำดับความสำคัญบนหน้าจอ และใบผลิต การตรวจอัตโนมัติไม่แทนการลองภารกิจจริงบนคอมและมือถือ เกณฑ์รับงานอยู่ใน SPEC

[GitHub CI](.github/workflows/ci.yml) รัน `npm ci`, lint, typecheck และ unit tests เมื่อเปิด PR หรือ push เข้า main ยังไม่รัน `verify:ui`, build หรือชุด integration ให้ จึงต้องตรวจเพิ่มตามงาน

```bash
npm run build
npm start
```

build สร้าง Prisma client และ Next.js production build ต้องมี env ที่จำเป็นตาม [src/lib/env.ts](src/lib/env.ts) ส่วน `npm start` เปิด build ที่สร้างแล้ว

คำสั่ง `verify:*` แต่ละตัวมีขอบเขตต่างกัน อ่าน [scripts](scripts) และ [package.json](package.json) ก่อนเลือก: หลายตัวสร้างหรือแก้ข้อมูล เชื่อม DB, Supabase หรือ Stock จริง ต้องใช้ฐานทดสอบที่อนุมัติแล้ว ไม่รันทั้งชุดกับฐาน Production ตัว `verify:supabase` อ่าน bucket และลอง list แบบ anon จึงตรวจได้เพียง bucket มีอยู่/เป็น private และ anon list ไม่เห็นรายการ; ผลผ่านไม่ยืนยันว่าปิด signup หรือมี Storage policy ถูกต้องครบ

ใช้ `npx tsx scripts/run-local-demo.ts check scripts/verify-ชื่อชุด.ts` เพื่อล็อก DB ของชุดตรวจไป `127.0.0.1:5433/anajak_erp_demo` และปิด Stock ภายนอก. ตัวเรียกยังอ่านค่า Auth/Storage จาก `.env`; ชุดอัปโหลดไฟล์จึงใช้ Storage เดิมและลบเฉพาะไฟล์ทดสอบเมื่อจบ. ชุด `verify-ui-public.ts prepare` สร้างข้อมูลสำหรับเปิดลิงก์/พิมพ์ใน browser, `expire` ทดสอบหมดอายุ, `cleanup` ล้างเฉพาะ fixture ตาม manifest ใน `.tmp-test` โดยไม่ reset ฐาน

## ตรวจสภาพแวดล้อมก่อนขึ้นใช้จริง

หัวข้อนี้เป็นขั้นตอนที่ต้องตรวจในแต่ละสภาพแวดล้อม ผลผ่าน วันที่ และงานที่ยังค้างเก็บที่ ROADMAP ไม่ถือว่าไฟล์ config หรือผลตรวจเก่าเป็นหลักฐานว่า Production ตั้งค่าครบแล้ว

### Supabase และไฟล์

1. ตรวจใน Supabase Authentication ว่าปิดการสมัครผู้ใช้สาธารณะ ระบบสร้างผู้ใช้จาก Settings → ผู้ใช้ การมีเพียง anon key เป็นค่าฝั่งเบราว์เซอร์ไม่ได้ทำให้คนนอกควรสมัครเองได้
2. ตรวจ bucket `designs` เป็น private และ policy ใน `storage.objects`: อนุญาต INSERT สำหรับ authenticated เฉพาะ bucket นี้ผ่าน `erp_staff_upload_designs`; ไม่มี SELECT/UPDATE/DELETE สำหรับ anon หรือ authenticated การอ่านและลบผ่านฝั่งเซิร์ฟเวอร์ ดู SQL ต้นทางที่ [docs/sql/storage-private-rollout.sql](docs/sql/storage-private-rollout.sql) และทบทวน policy เดิมก่อนใช้ SQL ซึ่งมีคำสั่งสร้าง policy
3. รัน `npm run verify:supabase` กับสภาพแวดล้อมที่ต้องตรวจ แล้วทดสอบพนักงานแนบไฟล์จากออเดอร์ เห็นภาพหลังอัปโหลด และเปิดลิงก์อนุมัติแบบในเบราว์เซอร์ที่ไม่ล็อกอิน ให้ภาพออกผ่าน `/api/files` พร้อม token ที่ถูกต้อง ตรวจสิทธิ์อ่านไฟล์จากบัญชีและ token ที่ไม่ควรเข้าถึงด้วย
4. ตรวจสำรองข้อมูลจาก Settings → สำรองข้อมูล โดย OWNER: export เป็น JSON ทุกตารางใน `public` จาก snapshot เดียวและมี audit ไฟล์นี้มีข้อมูลลับรวมค่าการเชื่อมต่อ จึงเก็บในพื้นที่สำรองที่จำกัดสิทธิ์ และไม่ใส่ Git

แนวทางสำรองที่ตกลงไว้คือใช้ export ในแอปสัปดาห์ละครั้งและหลังปิดเดือน โดยยังไม่อัปเกรด Pro พร้อมรักษาเอกสารภาษีตามข้อกำหนดโครงการใน SPEC ไฟล์จริงใน Storage และบัญชี Supabase Auth ไม่รวมใน JSON นี้ ต้องมีวิธีสำรองและทดสอบกู้คืนแยก หากจะใช้ backup อัตโนมัติหรือ PITR ให้ตรวจแผนบริการและค่าใช้จ่ายของสภาพแวดล้อมจริงก่อนเปลี่ยน

### Vercel และทางเข้าสาธารณะ

1. ตรวจ Git repository/branch ที่ผูกกับ Vercel และสภาพแวดล้อมปลายทางก่อนเผยแพร่ main ของโครงการนี้ใช้เป็นทางขึ้นเว็บจริง งานบน branch ต้องตรวจ preview และผล deploy ของ commit นั้นก่อน
2. ตรวจ env ของ Preview/Production ให้ชี้ฐานและ Supabase ที่ตั้งใจใช้ รวม `CRON_SECRET`, `NEXT_PUBLIC_APP_URL` และสวิตช์ V2; ตรวจ Stock จาก Settings → Stock และ env สำรองให้ไม่ชี้คนละระบบ
3. ตรวจงานตามเวลาใน [vercel.json](vercel.json) ทั้ง `/api/cron/overdue` และ `/api/cron/stock-reservations` จากผลเรียกจริง ไม่ถือว่ามี schedule เท่ากับรันสำเร็จ
4. ตั้งและตรวจ rate limit ของหน้าลิงก์สาธารณะ `/job/`, `/status/`, `/quote/`, `/approve/`, `/upload/` ตามแนวทางใช้ Vercel Firewall: เริ่มบันทึกอย่างเดียวด้วยกรอบ 60 คำขอต่อ 60 วินาทีต่อ IP ดูทราฟฟิกจริงก่อนเปลี่ยนเป็นจำกัดคำขอ และค่อยปรับลดหากมีหลักฐานรองรับ ตรวจขอบเขตตัวนับแต่ละ region และความสามารถของแผน/CLI ที่ใช้อยู่ก่อนเผยแพร่กฎ
5. ทบทวน Bot Protection/managed rules ในผู้ให้บริการ ตรวจว่าลูกค้าจริง การเปิดตัวอย่างลิงก์ใน LINE และตัวเก็บข้อมูลเว็บยังใช้งานได้ หลีกเลี่ยงการบล็อก path กว้างหรือปิดจาก user-agent อย่างเดียว ถ้าต้องนับต่อ token/cookie ต้องวางวิธีเพิ่มแยกก่อน
6. ก่อนเปลี่ยนงานการเงินจริงให้นักบัญชีตรวจ template ใบกำกับ ใบลดหนี้/เพิ่มหนี้ และเลขเอกสาร; ก่อนเปิด flow ใหม่ให้ทีมลองงานจริง รวมการเปลี่ยนไป Production V2 และทางกลับตามเกณฑ์ใน SPEC/ROADMAP

หลัง deploy ตรวจ URL ที่ผู้ใช้เปิดจริง สิทธิ์ของแต่ละบทบาท หน้าลิงก์สาธารณะ และรายการข้อมูลที่เปลี่ยนตามภารกิจ การผ่าน build หรือเห็น deployment สำเร็จเพียงอย่างเดียวยังไม่ยืนยันกระบวนการทำงานครบ
